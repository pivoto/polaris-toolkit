# commit 按规范生成概要并提交

分析当前 git 变更内容，按本项目提交规范生成中文提交信息，暂存相关文件并提交。

## 语言约定

全程使用中文：提交信息、说明一律中文；仅标识符、文件路径、命令保持原样。

## 提交信息规范

格式：

```
【<type>】<subject>

<body>

<footer>
```

- **head**：`【<type>】<subject>`，subject 为一句话概要（不加句号）。
- **body**（可选）：变更原因 / 解决方案 / 影响范围，分点或短段落。
- **footer**：固定追加 `Co-Authored-By: Claude Bot`。

### type 对照表

根据变更内容选择最贴切的类型：

| 中文 type | 英文 type | 适用场景 |
|--------|-----------|---------|
| 【功能新增】 | fea/feature | 新增特性 |
| 【功能变更】 | fea/feature | 变更或扩展增强已有功能特性 |
| 【功能优化】 | opt/optimize | 对已有功能的设计/实现/规范优化改进 |
| 【缺陷修复】 | fix/bugfix | 修复缺陷 |
| 【代码重构】 | refactor | 代码整体或局部重构 |
| 【性能优化】 | perf/performance | 强调性能优化 |
| 【文档更新】 | doc | 文档修改 |
| 【配置变更】 | conf | 工程/开发/运行配置变更 |
| 【代码测试】 | test | 测试代码增加或修改 |
| 【代码规范】 | style | 格式化、空白、标点、空行等 |
| 【项目构建】 | build | 构建脚本、CI、辅助工具 |
| 【依赖更新】 | dependency | 新增或更新依赖库版本 |
| 【版本发布】 | release | 版本发布 |
| 【版本快照】 | snapshot | 版本快照 |
| 【变更回退】 | revert | 变更回退 |
| 【其他杂项】 | chore | 不影响源码的其他杂项 |

> 默认使用中文 type；若仓库现有提交历史以英文 type 为主，则跟随既有风格。

## 工作流程

### 1. 检查变更状态

并行运行以下命令，全面了解变更：

```bash
git status --short          # 变更文件清单（含暂存/未暂存/未跟踪）
git diff --stat             # 已暂存变更的统计
git diff --cached --stat    # 同上（等价，二选一）
git diff --stat             # 未暂存变更的统计
```

若有未跟踪文件，用 `ls` / `Read` 粗看内容以判断归类。

### 2. 分析变更内容

根据 `git status` 与 `git diff` 判断：

- **type**：按对照表选择。若一个提交跨多个类型，选最主要的；若变更涉及多类无关改动，提醒用户可能需拆分多个提交（但默认仍按一次提交执行）。
- **subject**：用一句话概括本次变更做了什么（动词开头，如"新增…""优化…""修复…"），不加句号，简明扼要。
- **body**：必要时补充变更原因、解决方案、影响范围。

查看具体 diff 内容以准确归纳：

```bash
git diff --cached           # 已暂存的具体改动
git diff                    # 未暂存的具体改动
```

### 3. 暂存文件

若已有暂存内容则保留；若有未暂存的已跟踪改动需一并提交，则 `git add` 对应文件；若有未跟踪文件需提交，则 `git add` 它们。

> 默认将本次相关的全部变更一次性暂存并提交。若发现变更混杂多个无关关注点，先向用户说明并询问是否拆分，再执行。

### 4. 提交

用 heredoc 提交，保证 body 与 footer 格式正确：

```bash
git commit -m "【<type>】<subject>" -m "<body（可选）>" -m "Co-Authored-By: Claude <noreply@anthropic.com>"
```

或用 `$(cat <<'EOF' ... EOF)` 形式承载多行 body。**不要**用单个 `-m` 塞多行，易出错。

### 5. 反馈结果

提交后输出：

- commit 的短 hash 与分支；
- 本次提交信息（head + body）；
- 变更统计（文件数 / 增删行数）；
- 是否已推送（本 skill 仅本地提交，不推送；如需推送由用户另行指示）。

## 注意事项

- **只做本地提交，不 push**：除非用户明确要求推送。
- **不主动 rebase**：本 skill 不做 fetch/rebase；遵循本项目 rebase 工作流由用户在推送前自行处理。
- **空提交**：若无任何变更，直接告知用户"工作区干净，无需提交"，不要创建空提交。
- **当前分支**：若处于 `master`/`main` 等主分支，提交前提醒用户（但不阻断，由用户决定）。
- **提交信息字符**：subject 避免包含反引号、`$`、`"` 等 shell 特殊字符，或在 heredoc 中正确转义。
